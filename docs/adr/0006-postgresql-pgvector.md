# ADR-0006: 数据存储采用 PostgreSQL + pgvector

- **状态**: 已接受（2026-08-19）

## 背景

数据需求分两类：关系数据（企业/员工/Agent/Project/看板/审计日志/审批流）与向量数据（spec §3.1.2 项目级记忆、企业级 RAG 知识库）。选型决定运维形态与后续扩展边界。

## 决策

采用 **PostgreSQL 16 + pgvector 扩展**作为统一存储；ORM 用 Drizzle。

- 关系数据：常规表 + JSONB（Agent 配置、审计操作参数）
- 向量数据：pgvector（项目级记忆 embedding、企业知识库 chunk）
- 审计日志：结构化表 + 按时间分区（量大后可平滑迁移 ClickHouse，schema 设计保持列式友好）

## 理由

1. **运维最小化**：MVP 阶段一套数据库承载全部需求，私有化部署（spec §5.1 企业版）交付物最简。
2. **事务一致性**：权限审批流、看板状态、产出审核需要关系约束与事务，专用向量库不具备。
3. **pgvector 能力足够**：项目级/企业级记忆检索规模（百万级向量内）HNSW 索引性能可接受。

## 后果

- 正向：单实例备份恢复即可满足早期合规审计要求。
- 风险：企业知识库达千万级向量或需复杂过滤时性能受限——届时引入 Qdrant 作为项目级/企业级记忆专用层，接口已在 packages/core 中以 repository 抽象隔离。

## 备选方案

- **PostgreSQL + Qdrant**：检索更强，多一个运维组件，MVP 后置。
- **PostgreSQL + Milvus**：分布式海量向量，运维过重。
- **MySQL**：JSONB 与向量扩展生态弱于 PG。
