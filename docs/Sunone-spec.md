# 企业级 AI Agent 平台 — 产品规格书

> **版本**: v1.0  
> **状态**: 已确认（共享理解达成）  
> **日期**: 2026-08-19  
> **定位**: 企业级 AI OS — 管理 AI Agent 的权限与生命周期，让企业进入人机协同时代

---

## 一、愿景与理念

### 1.1 核心定位

未来的 AI Agent 将成为企业内的**基础设施**，如同今天的操作系统、数据库、网络一样不可或缺。

本平台不是面向个人的"AI 工作台"，而是面向企业的**AI 操作系统（AI OS）**：
- **执行上自下而上**：Agent 从终端用户设备出发，自主调用工具、完成任务
- **管理上自上而下**：管理层通过统一控制台监控、治理、配置全企业 AI 资源

### 1.2 使用展望

企业里的每名员工都配有一个或多个 Agents，Agents 进入企业的日常运转，处理大量工作。管理层可以监控 AI Agents 及其工作情况，量化业务价值产出。

```
├─────────────────────────────────────────────────────────────────────────────┤

│  │              WebSearch / WebFetch / Skill（调用专项技能）                   │

├─────────────────────────────────────────────────────────────────────────────┤
│  【协作层】Project 多人多 Agent 协作                                          │
│  ├── Project 空间：Owner 创建，邀请员工与 Agent，云端共享 Workspace           │           
│  ├── 内置轻量看板（类 Trello）+ 可选对接外部系统（Jira/Linear/Notion）       │
│  ├── Agent 间结构化消息通信（非自然语言），确保可追溯                         │
│  └── 产出审核：Agent 完成工作发起推送，Project Owner 审核通过/驳回并附理由   │
├─────────────────────────────────────────────────────────────────────────────┤
│  【安全层】多层防御与合规                                                     │
│  ├── 输入层：提示词注入检测（关键词 + 语义模型）                              │
│  ├── 规划层：策略引擎校验执行计划（LLM-as-a-Judge）                           │
│  ├── 执行层：沙箱硬隔离，即使恶意命令也无法突破进程边界                        │
│  ├── 审计层：异常行为模式检测（批量读取、敏感操作等）                          │
│  └── 分级响应：L1 告警员工 → L2 暂停 Agent 通知主管 → L3 隔离冻结通知安全团队 │

```

### 2.2 双端架构

| 端 | 形态 | 核心职责 | 技术选型 |
|---|---|---|---|
| **桌面端** | 本地安装（Electron/Tauri） | 执行引擎：Workspace 绑定、沙箱运行、文件操作、本地工具调用 | 必须在线（会话路由云端 LLM），本地执行不依赖云端 |
| **Web 端** | 浏览器访问 | 管理控制台：Project 看板、权限配置、监控面板、定时任务管理、审计查询 | 零部署、跨设备、管理层专用 |

**参考**：Cursor 的双端架构模式。

## 三、核心模块详解

### 3.1 基础核心 AI Agent

#### 3.1.1 原子工具（全加载）

Agent 可用的基础工具集合：

| 类别 | 工具 | 说明 |
|---|---|---|
| **文件操作** | Read / Write / Edit / Glob / Grep | 本地文件系统操作，受沙箱路径约束 |
| **执行操作** | Bash / PowerShell | Shell 命令执行，高危操作需确认 |
| **网络连接** | WebSearch / WebFetch | 网络信息获取 |
| **技能调用** | Skill | 调用专项技能模块 |

**权限模式**：
- **默认权限**：所有操作在沙箱约束内运行，关键操作（写文件、Shell、网络）需人工确认
- **完全访问**：减少确认步骤，但仍受企业策略黑名单约束

#### 3.1.2 记忆管理（三层架构）

| 层级 | 范围 | 持久化 | 技术 |
|---|---|---|---|
| **会话级** | 当前对话 | 临时 | 上下文窗口 |
| **项目级** | Project 内共享 | 持久 | 向量数据库（项目内资料共享） |
| **企业级** | 企业知识库 | 持久 | RAG 连接企业知识库（有知识库时启用） |

**自动召回**：根据任务相关性自动从三层记忆中召回信息。

#### 3.1.3 权限管理

**RBAC-ABAC 混合模型**：

| 层级 | 主体 | 管理方 | 说明 |
|---|---|---|---|
| **企业级** | 全局策略、黑名单、白名单 | IT 管理员 / 安全官 | 企业级 Deny 永远生效，不可覆盖 |
| **Project 级** | 项目成员、可用数据源、看板权限 | Project Owner | Agent 在 Project 中只能访问授权数据源 |
| **Agent 级** | 连接器引用、Skills、工具偏好 | 员工（Agent 所有者） | 在约束内自由配置 |

**权限冲突规则**：`企业级黑名单 > 企业级白名单 > Project 级限制 > Agent 级配置`

**权限提升流程**：
```
Agent 检测到权限不足
  → 自动生成申请单（含理由、范围、时长）
  → 发送给审批人（Project Owner 或 IT 管理员）
  → 审批通过后下发临时 Token（带过期时间）
  → 全链路审计记录
```

**审批优化**：连接器由 IT 管理员**预配置时一次性审批**，员工日常仅"一键启用"，**零审批风暴**。

#### 3.1.4 Skills 渐进式加载

**加载机制**：

| 层级 | 内容 | 加载时机 | 性能 |
|---|---|---|---|
| **索引层** | 技能名称 + 一句话描述 + location | 每次对话预置注入上下文 | 极轻量 |
| **内容层** | SKILL.md 完整指令 | 任务匹配且调用 Skill 工具时 | 按需加载 |

**强制规则**：匹配到技能时，必须先调用 Skill 工具加载其指令，再作答。

**三级仓库**：

| 仓库 | 来源 | 审核 | 共享范围 |
|---|---|---|---|
| **官方内置** | 平台提供 | 严格审核 | 全平台 |
| **企业私有** | 员工上传 | IT 管理员审核后发布 | 企业内 |
| **个人本地** | 员工自研 | 无需审核 | 仅自己 |

**Skills 资产化治理**：
- 使用企业资源（数据源、算力、时间）产出的 Skills 自动归入企业仓库
- 纯个人创意工具可保留私有
- 所有 Skills 带创建者署名，内部声誉体系
- 使用统计可视化（被使用次数、节省时间）
- 高质量 Skills 纳入最佳实践，创造者获绩效认可

**安全扫描**：上传时自动检测提示词注入、敏感操作，高风险 Skills 标记"需确认"。

**参考**：Claude Code、OpenClaw 的 Skills 实现。

#### 3.1.5 Agent 核心循环

```
用户输入
  → Agent 规划（生成执行计划）
  → 策略引擎校验（LLM-as-a-Judge，检查越权/风险）
  → 沙箱执行（工具调用在隔离环境运行）
  → 全链路审计记录（谁+何时+什么工具+目标+结果）
  → 结果返回用户
  → （如需确认）等待人工批准后继续
```

### 3.2 面向用户的会话页面

#### 3.2.1 功能设计

- **Workspace 选择**：选择当前任务执行的本地文件夹（个人模式）或 Project 云端空间
- **权限切换**：默认权限 / 完全访问（需确认）
- **Agent 选择**：切换已配置的不同 Agent（不同人设、Skills、连接器组合）
- **会话历史**：查看过往对话与执行记录

**参考**：Codex CLI、WorkBuddy、Claude Code 的交互模式。

### 3.3 Project：团队协作空间

#### 3.3.1 核心概念

- **创建**：由员工创建 Project，成为 Project Owner
- **邀请**：邀请其他员工及其 Agent 加入
- **Workspace**：Project 内共享云端文件夹，所有成员 Agent 可访问
- **看板**：内置轻量项目管理看板（类 Trello）

#### 3.3.2 看板功能

- **人工维护为主**：任务状态由人拖动更新
- **Agent 辅助**：Agent 完成工作后自动更新对应卡片状态
- **关键节点确认**："发布生产"等关键状态变更需人工确认
- **可选对接**：支持连接外部系统（Jira / Linear / Notion）同步状态

**看板作为共享上下文**：所有 Project 内 Agent 可读看板状态，协调任务。

#### 3.3.3 协调 Agent 模式

- Project Owner 可指定一个**项目经理 Agent**
- 负责：任务分解 → 分配给其他 Agent → 监控进度 → 汇总产出
- Agent 间通过**结构化消息**通信（非自然语言），确保可追溯
- 避免 Agent 自发协调导致的混乱

#### 3.3.4 产出审核流程

```
Agent 完成任务
  → 发起推送（提交产出到 Project）
  → Project Owner 审核
      ├── 通过 → 产出生效，看板状态更新
      └── 驳回 → 附理由，Agent 重新执行
```

**价值量化**：记录 Agent 运行工作时长，不采用硬性配置。Project Owner 审核产出有效性，无效产出不计入价值统计。

### 3.4 企业数据集成与权限管理

#### 3.4.1 连接器架构

| 属性 | 说明 |
|---|---|
| **形态** | 平台侧"受信服务"（非沙箱内运行） |
| **组成** | 内置主流连接器 + 开放 SDK 供企业自研 |
| **凭证管理** | IT 管理员统一配置 OAuth / Token，员工不可见 |
| **员工操作** | 在授权范围内"一键启用"到自己的 Agent |
| **预置系统** | GitHub、Jira、Confluence、Slack、飞书、钉钉、企业微信、SAP、Oracle 等 |

**部署模式**：
- 企业签约后，平台派出人员上门部署配置
- 重点：配置好企业内部知识库和数据源连接
- 目标：让企业内部真正用起来

#### 3.4.2 部署交付策略（产品化方向）

**当前状态**：上门部署，解决企业内部数据源异构性问题。

**规模化路径**：

| 层级 | 交付物 | 负责方 | 说明 |
|---|---|---|---|
| **平台层** | 标准化部署包（Docker / K8s Helm）、配置向导、健康检查 | 平台产品化 | 标准化 |
| **连接器层** | 预置主流系统模板，覆盖 80% 场景 | 平台维护 | 开箱即用 |
| **适配层** | 可视化字段映射工具（拖拽映射企业字段到标准模型） | 客户 IT 自助 | 降低定制 |
| **定制层** | 仅自研系统或极端老旧系统需人工介入 | 保留但压缩 | 顾问+培训角色 |

**关键转变**：部署人员从"手动配置者"变为"顾问+培训师"——教客户 IT 团队用工具自助完成，边际成本趋近于零。

### 3.5 定时任务

#### 3.5.1 触发方式

- **每日定时**：如"每天上午 9 点生成昨日数据报告"
- **频率触发**：如"每 30 分钟检查一次邮件并分类"

#### 3.5.2 执行架构（云端调度 + 本地执行混合）

```
云端调度器
  → 尝试唤醒员工在线桌面端
      ├── 在线 → 本地 Agent 执行
      └── 离线 → 按任务敏感度处理：
              ├── 非敏感任务 → 降级到云端沙箱执行（需 Agent 有云端权限）
              └── 敏感任务 → 排队等待设备上线，或转交 Project 内其他在线 Agent
```

**关键任务**：可配置"必须本地执行"策略。

### 3.6 安全管控

#### 3.6.1 沙箱设计

- **轻量级内核进程级隔离**
- **参考**：主流 WorkBuddy、Codex、DeepSeek Harness 的进程隔离轻量级设计
- **约束**：Agent 的所有文件/网络/Shell 操作在沙箱边界内，无法逃逸到宿主机其他区域

#### 3.6.2 多层防御体系

| 层级 | 机制 | 说明 |
|---|---|---|
| **输入层** | 提示词注入检测 | 关键词过滤 + 语义模型识别 |
| **规划层** | 策略引擎校验 | LLM-as-a-Judge，审查执行计划是否越权 |
| **执行层** | 沙箱硬隔离 | 即使 Agent 生成恶意命令，无法突破进程边界 |
| **审计层** | 异常行为检测 | 批量文件读取、敏感路径访问、异常网络请求等模式识别 |

**参考**：OpenAI Preparedness Framework。

---

### 3.7 全链路动作审计

#### 3.7.1 审计范围

覆盖 Agent 从触发到完成的完整生命周期，参考 DeepSeek Harness 设计。

#### 3.7.2 日志内容

| 字段 | 记录内容 | 脱敏规则 |
|---|---|---|
| 主体 | 员工 ID + Agent ID | 无 |
| 时间 | 操作时间戳 | 无 |
| 工具 | 调用的工具名称 | 无 |
| 目标资源 | 文件路径 / API 端点 / 网络域名 | 无 |
| 操作参数 | 工具输入参数 | 密码、Token 自动脱敏 |
| 文件操作 | 路径 + 内容摘要（hash） | 不记录全量内容（除非深度审计模式） |
| 网络请求 | 域名 + 状态码 | 不记录响应体（除非异常） |
| 结果 | 成功 / 失败 / 需确认 | 无 |

#### 3.7.3 分级响应

| 级别 | 异常类型 | 自动响应 |
|---|---|---|
| **L1** | 轻微越权尝试、单次异常 | 记录并告警员工 |
| **L2** | 多次失败、敏感操作尝试 | 暂停 Agent，通知主管 |
| **L3** | 疑似数据泄露、恶意行为 | 立即隔离 Agent，冻结 Workspace，通知安全团队 |

所有响应自动生成事件报告，纳入审计档案。

### 3.8 监控面板

#### 3.8.1 四级视图

| 角色 | 可见内容 | 隐私边界 |
|---|---|---|
| **员工** | 自己的 Agent 操作日志（脱敏后） | 仅自己的 |
| **Team Lead** | 团队成员聚合统计（操作次数、耗时、工具分布） | 不可见具体对话内容 |
| **IT 管理员** | 全链路技术日志（工具调用、异常、系统健康） | 可调查异常事件 |
| **高管** | 业务价值仪表盘（节省时间、ROI、Agent 累计工时） | 仅聚合指标 |

**对话内容**：默认加密，仅员工本人和授权审计员可调阅。

#### 3.8.2 核心指标

- **Token 消耗量**：按员工、按 Agent、按时间维度统计
- **使用记录**：全链路操作审计查询
- **Agent 累计工作时间**：实际运行时长
- **预计节省时间**：Agent 完成任务 × 人工替代系数（企业配置）
- **业务价值产出**：有效产出经 Project Owner 审核后计入

## 四、Agent 配置与管理

### 4.1 Agent 创建与配置

每个 Agent 是可配置的角色资源：

| 配置项 | 说明 |
|---|---|
| **人设设定** | 角色描述、行为风格、沟通方式 |
| **数据源连接** | 选择已授权的连接器（Jira、GitHub 等） |
| **Skills** | 选择已加载的技能包 |
| **工具开关** | 在默认权限/完全访问间切换 |
| **记忆绑定** | 关联项目级/企业级知识库 |

**企业级约束**：
- 企业级人设模板库由 HR/管理层维护
- 员工可在模板范围内微调
- 核心行为准则（代码规范、文档格式、沟通风格）由企业模板锁定
- Agent 产出不符合标准时，自动触发修正流程

### 4.2 Agent 生命周期

```
创建 → 配置（人设/连接器/Skills）→ 激活 → 执行任务 → 产出审核 → 价值统计 → 休眠/销毁
         ↑___________________________________________|
                    （持续迭代优化配置）
```

## 五、商业化与部署模式

### 5.1 产品版本

| 版本 | 目标客户 | 部署方式 | 计费模式 |
|---|---|---|---|
| **标准版** | 中小企业 | SaaS 多租户 | 按 Seat + Token 用量 |
| **企业版** | 金融/政务/大型集团 | 私有化单租户 | 按 Agent 实例数 + 年服务费 |
| **定制版** | 特殊需求企业 | 上门部署 + 定制开发 | 项目制 + 专属支持年费 |

**参考**：GitHub Enterprise 定价策略。

### 5.2 开源策略

- **开源**：Skills 规范、轻量级沙箱运行时
- **商业保留**：企业级审计、权限治理、监控面板、私有化部署支持、专属连接器
- **目标**：建立开发者生态，降低采用门槛

## 六、差异化定位

### 6.1 与 WorkBuddy 的差异

| 维度 | WorkBuddy | 本平台 |
|---|---|---|
| **定位** | AI 工作台（个人效率工具） | AI OS（企业基础设施） |
| **安全审计** | 基础 | 全链路留痕、分级响应、合规就绪 |
| **架构开放度** | 绑定腾讯生态 | 开放架构：任意模型、自研连接器 SDK |
| **部署模式** | SaaS 为主 | SaaS + 私有化 + 纯内网 |
| **管理维度** | 个人使用 | 自上而下企业治理 |
| **协作深度** | 基础共享 | Project 协调 Agent、结构化通信、产出审核 |

### 6.2 核心竞争壁垒

1. **全链路审计与合规**：金融/政务/上市公司的刚需
2. **开放架构**：不绑定单一云厂商或模型供应商
3. **私有化部署**：数据不出域，满足最高安全要求
4. **企业级治理**：权限、人设、Skills 的全局管控

## 八、关键术语表

| 术语 | 定义 |
|---|---|
| **AI OS** | 企业级 AI 操作系统，管理 Agent 权限与生命周期的基础设施平台 |
| **Agent** | 配置好的 AI 角色资源，包含人设、Skills、连接器配置 |
| **Workspace** | Agent 任务执行的物理/逻辑空间，个人模式绑定本地文件夹，Project 模式云端共享 |
| **Skills** | 专项能力包，包含 SKILL.md 指令，渐进式懒加载 |
| **连接器** | 对接企业内部系统的受信服务，由 IT 管理员统一配置 |
| **协调 Agent** | Project 内负责任务分解、分配、监控的项目经理 Agent |
| **沙箱** | 轻量进程级隔离环境，约束 Agent 的所有操作 |
| **全链路审计** | 覆盖 Agent 触发到完成完整生命周期的操作记录与监控 |
